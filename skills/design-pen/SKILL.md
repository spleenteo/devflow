# Flow: design adapter, Pen

The adapter `/flow:design` uses for `design: pen`: it says how to reach the Pen design tool and how its files are laid out. A project that prefers another tool replaces it with `design=<skill>` (`presets:` in `.flow.yml`, or `stack_presets`); nothing here is a command to the user.

## Requires

One of these, detected in this order:

1. The Pencil MCP tools: a tool of the session whose name ends in `get_app_state`, from a server whose name contains `pencil` (plugin servers are namespaced, so match the server name, not the full tool name). They read and write files with the app open.
2. The `pen` CLI, for headless work only: `command -v pen` succeeds.

Neither present: the requirement is not met. Say that the Pencil app's MCP tools or the `pen` CLI are missing, and that `/flow:design` goes on with Claude artifacts only.

## Files

- Extensions: `.pen` and `.lib.pen`.
- Role: a `.lib.pen` file is a library (the app's Libraries convention; nothing inside the file marks it). Any other `.pen` file is an area file, named after its area.
- Imports: a document-level field `imports`, `{"<alias>": "<file>"}`, with the file path relative to the importer. `execute` cannot set it: the app sets it (Libraries tab, **+**), or the CLI's `import_library` (see `### Import`). The alias is generated by the tool, never chosen.
- In-file note: a `note` node at the document's top level, saying what the file holds, so the file describes itself.
- Reading a file for the index (its `imports` and the names of its top-level frames): through the MCP tools, or, when only the CLI is present, through a headless `pen interactive` session.
- Files may be encrypted: never Read or Grep them. Open them only through the MCP tools or the CLI.

## Operations

Eight operations, in the order a design step uses them. `/flow:design` cites them as "the adapter's <Name>".

### Session

- With the MCP tools: pass `filePath` on every call; the app is open.
- With the CLI only: one session per file, run from the repo root, commands fed by a heredoc, ended by `save()` and `exit()`:

  ```bash
  pen interactive -i <file> -o <file> <<'EOF'
  ...commands...
  save()
  exit()
  EOF
  ```

  Reading only: `-o` points to a scratch copy, never the source, written in the same command as `-o "$(mktemp -d)/read.pen"`. Commands always come from the heredoc, never through a file. Nothing temporary is ever written inside the repo. Paths given to shell commands are relative to the working directory.
- One file per call, and one logical change per `execute` call. A failing call rolls back whole, `try` included. After a failure, re-read the nodes before anything else and never resend the snippet; retry through `edits` with the `editId`, as the tool asks.
- Library aliases are generated by the tool (for example `9`), never chosen: read them from `get_app_state` (`<alias>:<id>`) or `list_libraries()` (`id`), never assume one.

### Open

- `get_app_state` for the file's state.
- A new file: with the CLI, `pen interactive -o <new file>` with no `-i` starts an empty canvas and `save()` writes it. With the MCP tools, ask the user to create the file in the app.
- Top-level frames: `Get((n,c)=>{c.skipChildren();Print(n.id,n.name)})`.
- The file's imports and their aliases: from `get_app_state`, or `list_libraries()` in the CLI.

### List

- Components: `get_app_state`'s "Reusable components"; imported ones read `` `<alias>:<id>`: <name> ``.
- Tokens: `GetVariables()`, which gives `<alias>:<name>` for imported ones.

### Import

- With the MCP tools: ask the user to add the library in the app (Libraries tab, **+**), then confirm it with `get_app_state`.
- With the CLI only, on the user's ok: `import_library({ path })`, with `path` relative to the shell's working directory (not the edited file; the stored import is relative to the importer). Confirm with `list_libraries()`; if the command fails, fall back to asking the user in the app. Never edit the file's JSON by hand.
- Then read the alias back (Open); never assume it.

### Compose

- `Insert` frames into the area file.
- A library component is `{type:"ref", ref:"<alias>:<id>"}`, the alias read in Open; overrides go through `Update(<instance>+"/<alias>:<childId>", {...})`: inside an instance of a library component the child ids carry the alias too (without it the call fails with "not found" and rolls back).
- Token values are `"$<alias>:<token>"`.
- A local `reusable: true` component only for a new one the user approved.
- Never `Replace` or `Delete` an existing node unasked.

### Promote

Moves an approved local component into a library, in two calls, one per file. Not atomic.

- Preconditions, checked before the first call so a stop leaves nothing half-done: the area file imports the library; the component's child names are unique (the override remap goes by name); every token it uses exists in the library; every nested `ref` in the component uses the target library's alias (an instance from another library: stop and tell the user, because rewriting it to `ref: "<id>"` would break inside the target library).
- Call 1, in the library: `Insert` the component's tree at top level as `reusable: true`, with `$<alias>:x` written `$x` and any nested `ref: "<alias>:<id>"` written `ref: "<id>"`. Record the new id and the child ids by name.
- Between the calls, `get_app_state` on the area file must list `<alias>:<newId>`. If not (the file is open in the app on a stale copy), ask the user to reopen it, then check again.
- Call 2, in the area file: each instance of the local component is `Replace`d by `{type:"ref", ref:"<alias>:<newId>"}` that keeps the instance's own properties (name, position, size) and its `descendants` override keys remapped from old to new child id by child name (`Update` cannot change `ref`); then `Delete` the local component.
- If call 2 fails, the library holds the component and the area file still has its local copy. Say so and offer to finish with call 2 only, after re-reading both files. Never re-run call 1: it would duplicate the component.

### Note

The top-level `note` node: `Update` its content, or `Insert` one when missing. It says what the file holds (a library: its components; an area: its screens and imported library), in the language `/flow:design` passes.

### Export

`Export([<node ids>], "<format>", "<folder>")`, only on request. With the CLI, a relative `<folder>` is resolved from the `.pen` file's folder, not from the working directory, so pass an absolute folder: the repo root plus the folder the user named. Then check each absolute path it returns with `test -f`; a missing one is reported as failed.

## Cautions

- Save and close the files in the app before any branch switch, so unsaved work does not follow the checkout or collide with it.
- Moving a library breaks its importers' relative `imports` and image paths: move it together with its importers, or rewrite the import in the app afterwards.
- Resolve merge conflicts in the app by keeping both versions; never edit a `.pen` file by hand.
- Before any CLI session on a file, the user saves and closes it in the app, or the app's copy overwrites the change.
