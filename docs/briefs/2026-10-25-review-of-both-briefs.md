# Review of the two briefs (flow plugin, decisions log)

Checked against the repo at `/Users/spleenteo/Sites/me/devflow` (branch `chore/convert-to-plugin`, identical to `main` at 6d0ae6a) and the official Claude Code docs (manifest, marketplace, loading, host-marketplace, org, dependencies, skills pages; fetched 2026-10-25). "Verified" below means I read it in the docs; "belief" means I did not.

## Verdict

1. Brief 1 is sound in shape but its central promise ("a teammate gets the flow without installing anything, pinned per project") is only half true: the `flow` plugin itself does load from a trusted repo's settings, but every dependency (superpowers, shaping skills, grill-me) still needs a manual install, and one machine holds one copy of a marketplace, so two projects pinned to different tags fight over it. The spike must test this before the "Why" is written into the README.
2. Two naming facts are settled by the docs, not by a spike: a frontmatter `name:` changes only the last segment (`./devflow` + `name: dev` → `/flow:dev`), and the bare `/dev` also works when nothing else claims it. That same `name: dev` turns the `install.sh`/`npx` personal install into a bare `/dev` command, so the two install paths pull in opposite directions. Decide before opening, not at slicing.
3. The conductor-edits-itself problem is real and must be solved by a concrete recipe (worktree + symlinks left on `main`), not left as "say which".
4. One agnostic-ness violation the briefs miss: `projectflow/SKILL.md` names Maestro (the owner's tool) and `Cerbaia` (the owner's project) in three places.
5. Brief 2 is mostly fine; its two weak points are the gate script's location (use `${CLAUDE_SKILL_DIR}`, copy into the project for CI) and `resolved_by: <commit>` (use the work slug). Its paths and config name must be written as "whatever Work 1 decided", not as `.flow.yml`.

## Findings

### Blockers

**B1. Per-project tag pinning conflicts with one-marketplace-per-user.** · Brief 1, "Why" bullets 1–3 and "Facts" bullet 4 · Verified: `known_marketplaces.json` is per user ("a marketplace you add in one project is available in every project"); "each user registers one marketplace per `name`"; "a declared marketplace whose source changed in settings: Claude Code re-fetches it from the new source". Project A pinning `ref: v0.1.0` and project B pinning `ref: v0.2.0` on the same machine declare the same marketplace name with different sources; which wins (user vs project scope, project vs project) is not documented, and a relative-path plugin "loads from the marketplace copy", i.e. from whatever the clone currently is. The "one-line, reversible upgrade per project" story may hold only for one project per machine. · Fix: add to the spike: "two test repos pinned to different refs of this marketplace on one machine, plus a user-scope install at a third ref: which version loads in each, and what happens on switching." Rewrite "Why" after the spike. Fallback designs to mention in the brief: (a) pin at user scope and let projects only *enable*; (b) release channels as separate marketplace names (`flow-stable`, `flow-latest`), as the docs suggest for channels.

**B2. The conductor edits itself, and the rename breaks the symlinks mid-work.** · Brief 1, "Points of attention" bullet 1; repo `~/.claude/skills/{devflow,...}` → `<clone>/<skill>` · Changing the frontmatter `name:` in the symlinked folder immediately changes the personal command; moving folders (if the spike says so) makes `/devflow` disappear between sessions, and a resume reloads the half-rewritten `SKILL.md`. · Fix, concrete wording: "Run the work from `git worktree add ../devflow-flow chore/convert-to-plugin`; the main checkout stays on `main` so the four symlinks keep serving the frozen conductor. Nothing in `~/.claude/skills` is touched until the migration slice, which is the last one before the closing sequence." (Branch and `main` are identical today, so this costs nothing.)

**B3. The two install paths contradict each other on names.** · Brief 1, "What must come out" item 2 and spike bullets 2 and 6 · Verified (skills page): in a plugin, `name: fancy` gives `/my-plugin:fancy` and "the bare `/fancy` also works unless another command uses that name"; in `~/.claude/skills/`, "`name` sets the command ... The directory name also invokes the skill." So `./devflow` with `name: dev` yields `/flow:dev` (and bare `/dev`) as a plugin, and `/dev` plus `/devflow` from a symlinked personal install. There is no frontmatter value that gives `/flow:dev` in the plugin and a prefixed name in a personal install. · Fix: decide now (see D2). Recommended: folders become `skills/dev`, `skills/project`, `skills/changelog`, `skills/archive` with `name:` equal to the folder (needs no `skills` key in the manifest); `install.sh`/`npx` become secondary, documented as giving `/dev`, `/project` etc., or dropped in favour of `claude plugin marketplace add spleenteo/devflow#<tag>` + `claude plugin install flow@<marketplace>` for users outside a repo.

### Major

**M1. "superpowers can go in the same `enabledPlugins`" is wrong for teammates.** · Brief 1, spike bullet 7 and "Why" bullet 1 · Verified (loading, org): a plugin with an external source "doesn't install from the repository's settings alone"; each contributor sees `enabled in project settings but isn't installed` until they run `claude plugin install`. Only relative-path plugins load with trust alone. · Fix: replace the bullet with: "Only `flow` itself loads from trust. Test whether `dependencies: [{name: superpowers, marketplace: claude-plugins-official, version: ^7}]` in `plugin.json` plus `allowCrossMarketplaceDependenciesOn: ["claude-plugins-official"]` in `marketplace.json` installs superpowers when `flow` is first loaded from a trusted repo (the docs list install, `/reload-plugins`, auto-update and `marketplace add` as the moments dependencies install; repo trust is not in the list). Shaping skills and `grill-me` are not plugins: decide whether to vendor them (check licenses), list them as `github`-source entries in this marketplace (the entry becomes their manifest), or keep them as a documented manual step." The README must say plainly what a teammate gets with trust alone and what they still install.

**M3. "Plugin skills are always invoked with the namespace" is inaccurate.** · Brief 1, "Facts" bullet 3 · Verified: the bare name works when unique. **M4. Version: pick one source, and consider omitting `version` from `plugin.json`.** · Brief 1, "Points of attention" bullet 3 · Verified: "a manifest that pins `version: 1.0.0` keeps every user on the cached copy until its author changes the string, however many commits they push"; with no `version`, a relative-path plugin in a git-hosted marketplace is versioned by "the commit SHA of the installed directory". Since projects pin the marketplace `ref` to a tag, `version` adds nothing and creates the drift the brief fears (tag moves, manifest string doesn't, users stay on the old copy). · Fix: "`.version` + `docs/CHANGELOG.md`, written by the changelog skill in the closing sequence, are the human version; the git tag is `v<.version>`; `plugin.json` carries no `version`. Gate: `claude plugin validate . --strict` passes and `git tag` for the current `.version` doesn't already exist." Note `claude plugin validate` warns on a missing `version`/`description`/`author`, so `--strict` would fail; either accept warnings or add `description`/`author` and accept the `version` warning (verify which flags `--strict` escalates). Also note `claude plugin tag` creates `flow--v<version>` tags for dependency resolution, a different convention from `v<version>`; say which the repo uses (both is fine).

## Decisions for the owner

- **D1. Where does the conductor run from?** Recommended: a worktree for the branch; the main checkout stays on `main` with the symlinks untouched until the last slice.
- **D2. Folder layout and frontmatter names?** Recommended: `skills/{dev,project,changelog,archive}/SKILL.md`, `name:` equal to the folder, no `skills` key. Accept that personal installs give `/dev` etc., or drop them (D3).
- **D3. Keep `install.sh` and `npx skills add`?** Recommended: drop the symlink install; keep `install.sh` only as a dependency checker; document `claude plugin install flow@<marketplace> --scope user` for use outside repos (this also answers the `/flow:project` point).
- **D4. Versioning?** Recommended: no `version` in `plugin.json`; `.version` `0.1.0` and tag `v0.1.0`; projects pin `ref: v0.1.0`.
- **D5. Marketplace name?** Recommended: `flow` (plugin id `flow@flow`) is clean; otherwise `flow-plugins`. Note the release-channel fallback would need two names.
- **D6. Names of the two helper skills?** Recommended: `flow:changelog` and `flow:archive` as proposed; reserve `flow:docs`.
- **D7. Config file?** Recommended: `.flow.yml`, read `.devflow.yml` as fallback with a one-line notice.
- **D8. Dependencies story?** Recommended: declare superpowers as a cross-marketplace dependency if the spike shows it installs on first load; otherwise the README states the two manual commands. Don't vendor third-party skills without checking licenses.
- **D9. Brief 2 and `projectflow`?** Recommended: same kinds, status log, `## Reopen when`, headings; no `touches:` (no code), `area:` optional.
- **D10. Does Brief 2 stay one work?** Recommended: yes, but the `decisions-check` script and the project-copy mechanism are their own slice, last.
- **D11. First tag before or after Work 2?** Recommended: `v0.1.0` after Work 1; Work 2 ships as `v0.2.0` (format change is user-visible: MINOR).
